Making network retries safe in Parse SDK JS

Implementation notes, validation, and lessons from upstream contributions.

In Parse SDK JS PR #3170, I addressed a retry path where rejected fetch requests did not go through the existing retry handling. Retrying blindly would be dangerous because a failed connection does not prove a write was never applied.

Define what can be replayed

The fix limits eligible retries to reads and writes protected by an idempotency option, while excluding unprotected writes, streaming bodies, intentional aborts, and response-parsing errors. Network and HTTP failures share one attempt budget; the request ID remains stable across attempts.

Regression coverage

The PR adds 14 regression cases covering retry budgets, tunneled reads, idempotency, cancellation, and operations that must not be replayed. At submission, the reported local validation included 1,202 passing unit tests, lint, TypeScript checking, and a Node build. MongoDB-backed integration tests were not run.

Lesson

Resilience and correctness must be designed together: a retry is only safe when the client can establish that repeating the operation will not cause an unintended second effect. The change is under upstream review, not a claimed merged release.
